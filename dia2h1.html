15

Mover archivos entre el Directorio de trabajo y el Área de preparación

Ya aprendimos que git add permite llevar nuestros cambios desde el Directorio de trabajo hacia el Área de preparación.

Pero, ¿qué sucede si agregamos un archivo por error?

En esta práctica aprenderemos a preparar archivos y también quitar un archivo del Área de preparación sin eliminarlo de nuestro proyecto.

Paso 1

Creamos tres archivos nuevos.

Continuamos trabajando dentro de nuestra carpeta proyecto1 .

En Git Bash escribimos: 

touch contacto.html productos.html nosotros.html

Después presionamos Enter .

touch

En este ejercicio utilizamos touch para crear tres archivos de una sola vez: 

contacto.html
productos.html
nosotros.html
Paso 2

Revisamos el estado de los archivos.

Escribimos: 

git status

Después presionamos Enter .

Untracked files: 

contacto.html
nosotros.html
productos.html

Significa:
Git detectó los archivos nuevos, pero todavía no están preparados.

En este momento nuestros archivos se encuentran en el Directorio de trabajo.

Paso 3

Preparamos los tres archivos.

Queremos preparar todos los archivos al mismo tiempo. Escribimos: 

git add .

Después presionamos Enter .

DIRECTORIO DE TRABAJO

contacto.html
productos.html
nosotros.html

↓

git add .

↓

ÁREA DE PREPARACIÓN

Paso 4

Comprobamos que los archivos están preparados.

Escribimos nuevamente: 

git status

Después presionamos Enter .

Changes to be committed: 

new file:   contacto.html
new file:   nosotros.html
new file:   productos.html

Los archivos aparecen en verde.

Esto significa que los tres están preparados.

En este momento los tres archivos se encuentran en el Área de preparación.

Paso 5

Nos damos cuenta de que agregamos un archivo por error.

Tenemos un problema

Nosotros queríamos preparar contacto.html y productos.html.

Pero también agregamos por error: 

nosotros.html

¿Qué queremos hacer?

Queremos sacar nosotros.html del Área de preparación y dejarlo nuevamente en el Directorio de trabajo.

No queremos eliminar el archivo.

Paso 6

Quitamos nosotros.html del Área de preparación.

En Git Bash escribimos: 

git restore --staged nosotros.html

Después presionamos Enter .

git restore

restore significa restaurar.

--staged

Indica que queremos actuar sobre un cambio que se encuentra preparado en el Área de preparación.

nosotros.html

Es el archivo que queremos quitar del Área de preparación.

Por lo tanto:

git restore --staged nosotros.html

quita los cambios de nosotros.html del Área de preparación.

Paso 7

Comprobamos qué ocurrió.

Escribimos: 

git status

Después presionamos Enter .

Changes to be committed: 

new file:   contacto.html
new file:   productos.html

Estos dos archivos continúan en el Área de preparación.

Untracked files: 

nosotros.html

nosotros.html ya no está preparado.

Como es un archivo nuevo que todavía no pertenece a ningún commit, vuelve a aparecer como Untracked.

Importante: nosotros.html no fue eliminado. El archivo continúa dentro de nuestra carpeta proyecto1. Solamente dejó de estar preparado.

Paso 8

Entendemos el movimiento que realizamos.

DIRECTORIO DE TRABAJO

Archivo todavía no preparado

↓

git add .

↓

ÁREA DE PREPARACIÓN

Archivo preparado

↓

git restore --staged archivo

↓

DIRECTORIO DE TRABAJO

El archivo sigue existiendo, pero deja de estar preparado

¿Qué aprendimos?

git add nos permite preparar cambios y llevarlos al Área de preparación.

Si preparamos un archivo por error, podemos utilizar git restore --staged para quitar sus cambios del Área de preparación.

Esto no elimina el archivo de nuestra carpeta.

16

Volver del Repositorio local al Área de preparación

En la lección anterior dejamos contacto.html y productos.html preparados.

Ahora los guardaremos en nuestro Repositorio local mediante un commit.

Después simularemos un error: nos daremos cuenta de que todavía no queríamos realizar ese commit.

Aprenderemos cómo volver atrás sin perder nuestro trabajo.

Paso 1

Recordamos cómo terminamos la lección anterior.

Antes de continuar escribimos: 

git status

Debemos encontrar contacto.html y productos.html preparados.

Changes to be committed: 

new file:   contacto.html
new file:   productos.html

Estos dos archivos están en el Área de preparación.

Untracked files: 

nosotros.html

nosotros.html continúa en nuestro Directorio de trabajo y no está preparado.

Paso 2

Guardamos los archivos preparados.

Ahora queremos guardar los cambios que están preparados. Para ello realizamos un commit.

Escribimos: 

git commit -m "Agregamos contacto y productos"

Después presionamos Enter .

ÁREA DE PREPARACIÓN

contacto.html
productos.html

↓

git commit

↓

REPOSITORIO LOCAL

Paso 3

Comprobamos qué ocurrió.

Escribimos: 

git status

Ahora contacto.html y productos.html ya no aparecerán como cambios preparados porque fueron incluidos en el commit.

Importante: nosotros.html seguirá apareciendo como Untracked, porque no lo preparamos y, por lo tanto, no fue incluido en el commit.

Paso 4

Revisamos nuestro historial.

Para comprobar que se creó el nuevo commit escribimos: 

git log --oneline

El nuevo commit aparecerá en la primera línea. Veremos algo parecido a: 

xxxxxxx (HEAD -> master) Agregamos contacto y productos
b720efd Agregamos estilos y script
a4b383a Primer commit

El código xxxxxxx es solamente un ejemplo. Git generará un identificador diferente en cada computadora.

Paso 5

Nos damos cuenta de que cometimos un error.

Tenemos un problema

Acabamos de realizar el commit: 

Agregamos contacto y productos

Pero nos damos cuenta de que todavía no queríamos guardar esos cambios en el Repositorio local.

¿Qué queremos hacer?

Queremos deshacer solamente el último commit y regresar sus cambios al Área de preparación.

Pero queremos conservar nuestros archivos y nuestro trabajo.

Paso 6

Volvemos un commit atrás.

Para deshacer el último commit y conservar sus cambios preparados, escribimos: 

git reset --soft HEAD~1

Después presionamos Enter .

git reset

reset significa restablecer. En este ejercicio lo utilizamos para mover nuestra posición hacia el commit anterior.

--soft

Le indica a Git que queremos deshacer el commit, pero conservar sus cambios preparados.

HEAD

HEAD representa nuestra posición actual en el historial.

~1

Indica que queremos movernos un commit hacia atrás.

Podemos entender:

git reset --soft HEAD~1

como:

“Vuelve un commit atrás, pero conserva los cambios preparados.”

Paso 7

Comprobamos que los cambios regresaron.

Ahora escribimos: 

git status

Nuevamente debemos encontrar:

Changes to be committed: 

new file:   contacto.html
new file:   productos.html

Los cambios de estos dos archivos regresaron al Área de preparación.

Untracked files: 

nosotros.html

nosotros.html no formaba parte del commit, por eso continúa sin preparar.

Paso 8

Revisamos nuevamente el historial.

Para comprobar que el último commit fue retirado del historial actual, escribimos: 

git log --oneline

Ahora volveremos a ver como último commit: 

b720efd (HEAD -> master) Agregamos estilos y script

a4b383a Primer commit

El commit “Agregamos contacto y productos” ya no aparece en el historial actual.

Paso 9

Entendemos el movimiento que realizamos.

ÁREA DE PREPARACIÓN

contacto.html
productos.html

↓

git commit

↓

REPOSITORIO LOCAL

Los cambios forman parte del último commit

↓

git reset --soft HEAD~1

↓

ÁREA DE PREPARACIÓN

Conservamos los cambios preparados

Importante

En esta práctica utilizamos
git reset --soft HEAD~1 porque queremos conservar nuestro trabajo.

Por ahora no utilizaremos otras formas de reset porque primero debemos comprender correctamente este movimiento.

¿Qué aprendimos?

Con git commit llevamos los cambios preparados al Repositorio local.

Si acabamos de realizar un commit y necesitamos volver atrás, git reset --soft HEAD~1 permite mover nuestra posición al commit anterior y mantener los cambios del commit deshecho en el Área de preparación.

17

Reorganizar nuestros últimos commits

Hasta ahora aprendimos a crear archivos, prepararlos y guardarlos mediante commits.

Pero en un proyecto real podemos realizar varios commits y después darnos cuenta de que los últimos cambios todavía no estaban organizados correctamente.

En esta práctica crearemos varios commits y después aprenderemos a retroceder dos commits sin perder nuestros archivos, para poder organizarlos nuevamente.

¿Desde dónde comenzamos?

Al terminar la práctica anterior tenemos:

ÁREA DE PREPARACIÓN

contacto.html

productos.html

DIRECTORIO DE TRABAJO

nosotros.html

Archivo sin seguimiento

Paso 1

Creamos un commit con contacto y productos.

contacto.html y productos.html ya se encuentran preparados.

Por lo tanto, podemos guardarlos escribiendo: 

git commit -m "Agregamos contacto y productos"

Después presionamos Enter .

Git guardará solamente los archivos que estaban preparados. Por eso nosotros.html todavía no será incluido.

Paso 2

Preparamos nosotros.html.

Ahora queremos preparar nosotros.html.

Escribimos: 

git add nosotros.html

Después presionamos Enter .

DIRECTORIO DE TRABAJO

nosotros.html

↓

git add nosotros.html

↓

ÁREA DE PREPARACIÓN

nosotros.html

Paso 3

Creamos nuestro siguiente commit.

Como nosotros.html ya está preparado, escribimos: 

git commit -m "Agregamos nosotros"

Después presionamos Enter .

Ahora tenemos un nuevo commit que contiene nosotros.html.

Paso 4

Creamos dos archivos nuevos.

Nuestro proyecto continúa creciendo. Ahora crearemos: servicios.html y galeria.html.

Escribimos: 

touch servicios.html galeria.html

Después presionamos Enter .

Los archivos fueron creados, pero todavía estarán sin seguimiento.

Paso 5

Preparamos los dos archivos nuevos.

Escribimos: 

git add servicios.html galeria.html

Después presionamos Enter .

Al escribir los nombres de los dos archivos después de git add, estamos preparando específicamente esos dos archivos.

Paso 6

Creamos otro commit.

Guardamos los dos archivos preparados: 

git commit -m "Agregamos servicios y galeria"

Después presionamos Enter .

Paso 7

Revisamos todos nuestros commits.

Antes de continuar queremos observar cómo quedó nuestro historial. Escribimos: 

git log --oneline

Veremos algo parecido a:

xxxxxxx Agregamos nosotros

xxxxxxx Agregamos contacto y productos

b720efd Agregamos estilos y script

a4b383a Primer commit

Los identificadores marcados como xxxxxxx serán diferentes en cada computadora.

Paso 8

Nos damos cuenta de que los dos últimos commits no eran adecuados.

Tenemos un problema

Después de revisar nuestro historial nos damos cuenta de que realizamos demasiado pronto estos dos commits:

Agregamos servicios y galeria

Agregamos nosotros

Queremos retirar esos dos commits del historial actual, pero no queremos perder los archivos.

Paso 9

Retrocedemos dos commits.

En la lección anterior utilizamos HEAD~1 para retroceder un commit.

Ahora necesitamos retroceder dos commits. Escribimos: 

git reset --soft HEAD~2

Después presionamos Enter .

HEAD~2

Significa que queremos mover nuestra posición actual dos commits hacia atrás.

--soft

Permite retroceder en el historial conservando preparados los cambios de los commits retirados.

ANTES

↓

Agregamos nosotros

↓

Agregamos contacto y productos

↓

git reset --soft HEAD~2

↓

AHORA HEAD VUELVE A

Agregamos contacto y productos

Paso 10

Comprobamos que nuestros archivos no se perdieron.

Ejecutamos: 

git status

Los archivos de los dos commits que acabamos de retirar aparecerán preparados:

Changes to be committed: 

new file:   galeria.html
new file:   nosotros.html
new file:   servicios.html

Los dos commits fueron retirados del historial actual, pero nosotros.html, servicios.html y galeria.html no fueron eliminados.

Sus cambios quedaron nuevamente en el Área de preparación.

Paso 11

Decidimos reorganizar los archivos.

Ahora tenemos tres archivos preparados: 

galeria.html
nosotros.html
servicios.html

Supongamos que decidimos que nosotros.html todavía no está listo.

Lo sacamos del Área de preparación: 

git restore --staged nosotros.html

ÁREA DE PREPARACIÓN

servicios.html

galeria.html

DIRECTORIO DE TRABAJO

nosotros.html

Paso 12

Creamos un nuevo commit mejor organizado.

Ahora solamente servicios.html y galeria.html están preparados.

Creamos un nuevo commit: 

git commit -m "Agregamos servicios y galeria"

Después presionamos Enter .

Esta vez nosotros.html no será incluido porque lo sacamos previamente del Área de preparación.

Paso 13

Revisamos cómo quedó nuestro proyecto.

Primero revisamos el estado: 

git status

nosotros.html volverá a aparecer como archivo sin seguimiento, porque es un archivo nuevo que ya no forma parte de ningún commit del historial actual.

Untracked files: 

nosotros.html

Después podemos revisar nuevamente el historial: 

git log --oneline

Ahora tendremos un historial reorganizado parecido a: 

xxxxxxx (HEAD -> master) Agregamos servicios y galeria

xxxxxxx Agregamos contacto y productos

b720efd Agregamos estilos y script

a4b383a Primer commit

Observa que “Agregamos nosotros” ya no aparece en el historial actual. Sin embargo, nosotros.html continúa existiendo en nuestra carpeta.

¿Qué aprendimos?

Con git reset --soft HEAD~2 podemos retroceder dos commits y conservar preparados los cambios que pertenecían a esos commits.

Después podemos utilizar git restore --staged para decidir qué archivos todavía no queremos preparar.

Finalmente podemos crear nuevos commits mejor organizados sin perder nuestros archivos.

18

Modificar el mensaje del último commit

Cuando realizamos un commit escribimos un mensaje que nos ayuda a recordar qué cambios guardamos.

Pero podemos equivocarnos o darnos cuenta después de que el mensaje podría estar mejor escrito.

En esta práctica aprenderemos a modificar el mensaje del último commit utilizando --amend.

Paso 1

Revisamos nuestro historial.

Primero necesitamos observar cuál es nuestro último commit.

En Git Bash escribimos: 

git log --oneline

Después presionamos Enter .

Paso 2

Observamos nuestro último commit.

En nuestra práctica obtenemos: 

1a53cb3 (HEAD -> master) Agregamos servicios y galeria

1350112 Agregamos contacto y productos

b720efd Agregamos estilos y script

a4b383a Primer commit

Nuestro último commit tiene el identificador: 1a53cb3

Su mensaje es:
Agregamos servicios y galeria

Además, HEAD -> master nos indica que estamos posicionados en ese último commit de nuestra rama master.

Paso 3

Nos damos cuenta de que queremos mejorar el mensaje.

Queremos corregirlo

Actualmente nuestro mensaje dice: 

Agregamos servicios y galeria

Queremos reemplazarlo por un mensaje más claro: 

Agregamos páginas de servicios y galería

No queremos borrar servicios.html ni galeria.html. Solamente queremos corregir el mensaje del último commit.

Paso 4

Modificamos el mensaje del último commit.

En Git Bash escribimos: 

git commit --amend -m "Agregamos páginas de servicios y galería"

Después presionamos Enter .

Paso 5

Entendemos el comando.

git commit

Indica que estamos trabajando con un commit.

--amend

amend significa corregir, modificar o enmendar.

En esta práctica permite reemplazar el último commit por una versión con el mensaje corregido.

-m

Nos permite escribir directamente el nuevo mensaje del commit.

"Agregamos páginas de servicios y galería"

Es el nuevo mensaje que queremos utilizar.

Paso 6

Observamos la respuesta de Git.

Después de ejecutar el comando, en nuestra práctica Git muestra: 

[master d723ba8] Agregamos páginas de servicios y galería
 Date: Sat Sep 19 11:16:40 2026 -0400
 2 files changed, 0 insertions(+), 0 deletions(-)
 create mode 100644 galeria.html
 create mode 100644 servicios.html

d723ba8 es el nuevo identificador del commit.

2 files changed indica que este commit contiene dos archivos: galeria.html y servicios.html.

Aparece 0 insertions(+), 0 deletions(-) porque nuestros archivos continúan vacíos.

Paso 7

Comprobamos el cambio en el historial.

Para comprobar el resultado escribimos nuevamente: 

git log --oneline

Ahora obtenemos: 

d723ba8 (HEAD -> master) Agregamos páginas de servicios y galería

1350112 Agregamos contacto y productos

b720efd Agregamos estilos y script

a4b383a Primer commit

El mensaje anterior
“Agregamos servicios y galeria” ya no aparece.

Ahora aparece:
“Agregamos páginas de servicios y galería”.

Paso 8

Observamos que también cambió el identificador.

Antes de modificar el mensaje teníamos: 

1a53cb3 Agregamos servicios y galeria

Después de utilizar --amend tenemos: 

d723ba8 Agregamos páginas de servicios y galería

¿Por qué cambió de 1a53cb3 a d723ba8?

Porque el identificador pertenece al contenido y a la información del commit.

Al cambiar el mensaje, Git genera un nuevo commit que reemplaza al anterior en el historial actual.

Por eso también obtenemos un nuevo identificador.

Observemos el cambio

ANTES

1a53cb3

Agregamos servicios y galeria

↓

git commit --amend -m "Agregamos páginas de servicios y galería"

↓

DESPUÉS

d723ba8

Agregamos páginas de servicios y galería

Importante

git commit --amend modifica el último commit.

En esta práctica no estamos modificando commits anteriores del historial. Estamos corrigiendo solamente el commit donde actualmente se encuentra HEAD.

¿Qué aprendimos?

Si nos equivocamos en el mensaje del último commit, podemos corregirlo utilizando: 

git commit --amend -m "Nuevo mensaje"

Después utilizamos git log --oneline para comprobar el resultado.

En nuestra práctica el commit cambió de 1a53cb3 a d723ba8 porque al modificar el mensaje Git generó una nueva versión del último commit.

19

Modificar el mensaje de un commit anterior

En la lección anterior aprendimos a modificar el mensaje del último commit utilizando git commit --amend.

Pero también podemos descubrir un error en el mensaje de un commit anterior.

En esta práctica modificaremos el mensaje del tercer commit contando desde arriba utilizando un rebase interactivo.

Paso 1

Revisamos nuestro historial.

Antes de modificar un commit anterior necesitamos identificarlo. Escribimos: 

git log --oneline

De acuerdo con nuestra práctica, tenemos: 

d723ba8 (HEAD -> master) Agregamos páginas de servicios y galería

1350112 Agregamos contacto y productos

b720efd Agregamos estilos y script

a4b383a Primer commit
Paso 2

Identificamos el commit que queremos modificar.

Queremos modificar el mensaje: 

b720efd Agregamos estilos y script

Si contamos desde arriba, este es nuestro tercer commit:

1. Agregamos páginas de servicios y galería

2. Agregamos contacto y productos

3. Agregamos estilos y script
⬆ queremos modificar este

4. Primer commit

Paso 3

Iniciamos un rebase interactivo.

Como queremos trabajar con los últimos tres commits, escribimos: 

git rebase -i HEAD~3

Después presionamos Enter .

git rebase

Nos permite reorganizar o modificar una parte del historial de commits.

-i

Significa interactive, en español interactivo.

Git nos permitirá decidir qué queremos hacer con cada commit.

HEAD~3

Indica que queremos trabajar con los últimos tres commits anteriores a nuestra posición actual.

Paso 4

Git abre Nano con los commits seleccionados.

Se abrirá el editor Nano y veremos: 

pick b720efd Agregamos estilos y script

pick 1350112 Agregamos contacto y productos

pick d723ba8 Agregamos páginas de servicios y galería

Observa algo importante

En git log --oneline vimos primero el commit más reciente.

En el rebase interactivo Git los presenta del más antiguo al más reciente.

Por eso b720efd aparece ahora en la primera línea.

Paso 5

Cambiamos pick por reword.

Queremos cambiar solamente el mensaje del commit: 

Agregamos estilos y script

Por eso, en esa línea borramos solamente la palabra pick y escribimos: 

reword

Debe quedar así: 

reword b720efd Agregamos estilos y script

pick   1350112 Agregamos contacto y productos

pick   d723ba8 Agregamos páginas de servicios y galería

reword significa volver a escribir el mensaje.

Los otros commits permanecen con pick porque no queremos cambiar su contenido ni su mensaje.

Paso 6

Guardamos los cambios en Nano.

Después de cambiar pick por reword, debemos guardar el archivo.

Presionamos:

Ctrl + O

En Nano, Ctrl + O guarda el archivo.

Nano mostrará el nombre del archivo en la parte inferior. No necesitamos cambiarlo.

Presionamos:

Enter

Finalmente salimos de Nano:

Ctrl + X
Paso 7

Git nos pide escribir el nuevo mensaje.

Git se detendrá en el commit que marcamos con reword y abrirá nuevamente el editor.

Encontraremos el mensaje anterior: 

Agregamos estilos y script

Lo reemplazamos, por ejemplo, por: 

Agregamos archivos de estilos y JavaScript
Paso 8

Guardamos el nuevo mensaje.

Volvemos a guardar utilizando la misma secuencia:

Ctrl + O

↓

Enter

↓

Ctrl + X

Git continuará automáticamente con los demás commits.

Paso 9

Comprobamos el nuevo historial.

Cuando Git termine, escribimos: 

git log --oneline

Ahora veremos el mensaje corregido: 

xxxxxxx (HEAD -> master) Agregamos páginas de servicios y galería

xxxxxxx Agregamos contacto y productos

xxxxxxx Agregamos archivos de estilos y JavaScript

a4b383a Primer commit
Paso 10

Observamos qué ocurrió con los identificadores.

Antes teníamos: 

d723ba8 Agregamos páginas de servicios y galería
1350112 Agregamos contacto y productos
b720efd Agregamos estilos y script
a4b383a Primer commit

Después del rebase veremos identificadores nuevos desde el commit que modificamos hacia adelante.

¿Por qué también cambian los commits posteriores?

Los commits de Git están relacionados entre sí.

Cuando modificamos un commit anterior, Git tiene que reconstruir los commits que vienen después.

Por eso sus identificadores también cambian, aunque sus mensajes continúen iguales.

¿Qué hicimos?

Último commit

↓

Segundo commit

↓

Tercer commit

Agregamos estilos y script

↓

git rebase -i HEAD~3

↓

pick → reword

↓

Agregamos archivos de estilos y JavaScript

Importante

git rebase -i modifica el historial de Git.

Por ahora lo utilizaremos únicamente en nuestro repositorio local de práctica para comprender cómo funciona.

¿Qué aprendimos?

Para cambiar el mensaje del último commit podemos utilizar git commit --amend.

Pero si queremos modificar el mensaje de un commit anterior, podemos utilizar un rebase interactivo: 

git rebase -i HEAD~3

Después cambiamos pick por reword en el commit cuyo mensaje queremos modificar.

20

Usar .gitignore de forma práctica

En nuestro proyecto existe una página llamada nosotros.html.

Esta página sí forma parte de nuestro sitio web, por lo tanto debemos guardarla en Git.

Después crearemos un archivo temporal llamado borrador.txt. Ese archivo no será parte del sitio web y aprenderemos a ignorarlo utilizando .gitignore.

¿Desde dónde comenzamos?

Al finalizar la lección anterior tenemos cuatro commits en nuestro historial. Además, Git detecta una página llamada nosotros.html.

Importante

nosotros.html es una página real de nuestro proyecto. Por eso no debemos ignorarla.

Paso 1

Guardamos la página nosotros.html.

Primero agregamos la página al Área de preparación. Después creamos un commit para guardarla en el repositorio local. 

git add nosotros.html
git commit -m "Agregamos página nosotros"

Ahora nosotros.html ya forma parte de nuestro proyecto y de su historial de commits.

Paso 2

Creamos un archivo temporal.

Ahora crearemos un archivo que servirá únicamente para escribir ideas, pruebas o anotaciones personales.

Este archivo no forma parte de nuestra página web y no queremos guardarlo en Git. 

touch borrador.txt

¿Qué hace touch?

El comando touch crea un archivo vacío.

En este caso creará un archivo llamado borrador.txt.

Paso 3

Revisamos el estado del proyecto.

Ahora preguntamos a Git si encontró algún archivo nuevo: 

git status

Git mostrará el archivo borrador.txt dentro de la sección Untracked files. 

Untracked files:
  borrador.txt

¿Qué significa Untracked files?

Significa archivos no rastreados.

Git encontró el archivo dentro de nuestro proyecto, pero todavía no lo agregamos con git add ni lo guardamos en un commit.

Paso 4

Conocemos git status --short.

Git también puede mostrar el estado de manera más corta: 

git status --short
?? borrador.txt

¿Qué significa --short?

La opción --short le pide a Git que muestre un resultado breve.

En vez de mostrar una explicación larga, Git utiliza símbolos junto al nombre del archivo.

¿Qué significan los signos ???

Los símbolos ?? indican que Git encontró un archivo nuevo, pero todavía no lo está siguiendo.

En nuestro ejemplo, Git encontró borrador.txt, pero aún no fue agregado al Área de preparación.

Paso 5

Creamos el archivo .gitignore.

Ahora crearemos un archivo especial que le indicará a Git qué archivos no queremos guardar. 

touch .gitignore

El punto al inicio del nombre es importante: .gitignore es el nombre exacto que Git reconoce.

Paso 6

Abrimos .gitignore con Nano.

Ahora abrimos el archivo para escribir la regla: 

nano .gitignore

¿Qué hace Nano?

nano es un editor de texto que funciona dentro de Git Bash.

Nos permite abrir un archivo, escribir contenido, guardarlo y salir sin usar otro programa.

Paso 7

Escribimos la regla para ignorar el borrador.

Dentro de Nano escribimos el nombre exacto del archivo que no queremos guardar: 

borrador.txt

Esta línea significa: Git no debe guardar el archivo borrador.txt.

Guardamos y salimos de Nano

1. Presionamos Ctrl + O para guardar.

2. Presionamos Enter para confirmar.

3. Presionamos Ctrl + X para salir.

Paso 8

Comprobamos qué cambió.

Volvemos a revisar el estado normal del proyecto: 

git status

Git ya no mostrará borrador.txt. Ahora solo mostrará el archivo .gitignore: 

Untracked files:
  .gitignore

¿Qué ocurrió?

borrador.txt todavía existe en nuestra computadora, pero Git dejó de mostrarlo porque ahora está incluido en .gitignore.

Paso 9

Mostramos el archivo ignorado.

Normalmente Git oculta los archivos ignorados. Si queremos comprobar que realmente los está ignorando, escribimos: 

git status --ignored --short

¿Qué significa --ignored?

La opción --ignored le pide a Git que también muestre los archivos que está ignorando.

Usamos nuevamente --short para que el resultado sea breve. 

?? .gitignore
!! borrador.txt

¿Qué significan los signos !!?

Los símbolos !! indican que Git está ignorando correctamente ese archivo.

En este caso Git ignora borrador.txt.

Paso 10

Guardamos .gitignore en Git.

El archivo .gitignore forma parte del proyecto porque contiene reglas importantes. Por eso sí debemos guardarlo en Git: 

git add .gitignore
git commit -m "Agregamos archivo gitignore"

Git guardará .gitignore, pero no guardará borrador.txt.

¿Qué hicimos?

Guardamos nosotros.html

21

Ignorar varios archivos y una carpeta

En la lección anterior utilizamos .gitignore para ignorar un solo archivo:

borrador.txt

Pero en un proyecto real podemos tener varios archivos del mismo tipo o una carpeta completa que no queremos guardar en Git.

En esta práctica aprenderemos a ignorar todos los archivos terminados en .log y también una carpeta llamada temporal/.

¿Desde dónde comenzamos?

Al terminar la lección anterior, nuestro archivo .gitignore contiene una regla para ignorar únicamente borrador.txt: 

borrador.txt

Ahora agregaremos nuevas reglas sin eliminar la que ya tenemos.

Paso 1

Creamos dos archivos de registro.

Un archivo de registro guarda información sobre errores o actividades de un programa. Generalmente termina en .log.

Crearemos dos archivos de ejemplo: 

touch errores.log
touch prueba.log

Recordemos qué hace touch

El comando touch crea un archivo vacío.

En este caso crea los archivos errores.log y prueba.log.

Paso 2

Creamos una carpeta temporal.

También crearemos una carpeta para guardar archivos de prueba. Esta carpeta no formará parte de nuestro sitio web. 

mkdir temporal
touch temporal/notas.txt

¿Qué significa mkdir?

El comando mkdir significa crear carpeta.

En este caso crea una carpeta llamada temporal.

¿Qué significa temporal/notas.txt?

La barra / indica que el archivo notas.txt se creará dentro de la carpeta temporal.

Paso 3

Revisamos los archivos nuevos.

Antes de actualizar .gitignore, Git todavía detectará todos estos elementos como archivos nuevos: 

git status --short
?? errores.log
?? prueba.log
?? temporal/

Recordemos qué significa ??

Los símbolos ?? indican que Git encontró archivos nuevos, pero todavía no los está siguiendo.

Paso 4

Abrimos el archivo .gitignore.

Abrimos nuevamente .gitignore para agregar dos nuevas reglas: 

nano .gitignore

Dentro de Nano veremos la regla que ya creamos en la lección anterior: 

borrador.txt
Paso 5

Agregamos las nuevas reglas.

Borramos borrador.txt, y lo remplazamos por el siguiente contenido: 


# Ignorar el archivo borrador.txt                            
borrador.txt

# Ignorar archivos de registro
*.log

# Ignorar carpeta temporal
temporal/

¿Qué significa #?

Una línea que comienza con # es un comentario.

Git no usa los comentarios como reglas. Solo sirven para explicar qué hace cada grupo de líneas.

¿Qué significa *.log?

El símbolo * representa cualquier nombre.

Entonces la regla *.log significa: ignorar todos los archivos que terminen en .log. 

Se ignora:
errores.log
prueba.log
registro.log

¿Qué significa temporal/?

La barra final / indica que temporal es una carpeta.

La regla temporal/ ignora la carpeta y también todos los archivos que estén dentro de ella.

Paso 6

Guardamos y salimos de Nano.

1. Presionamos Ctrl + O

Para guardar los cambios.

2. Presionamos Enter

Para confirmar el nombre .gitignore.

3. Presionamos Ctrl + X

Para salir de Nano.

Paso 7

Comprobamos el resultado.

Ahora Git ya no debe mostrar los archivos .log ni la carpeta temporal: 

git status --short
 M .gitignore

¿Qué significa M?

La letra M significa Modified, es decir, modificado.

Git indica que modificamos el archivo .gitignore, pero todavía no lo agregamos al Área de preparación.

El espacio vacío antes de la letra M indica que todavía no usamos git add.

Paso 8

Mostramos los archivos ignorados.

Usamos el siguiente comando para comprobar que Git está ignorando todos los archivos y la carpeta: 

git status --ignored --short
 M .gitignore
!! borrador.txt
!! errores.log
!! prueba.log
!! temporal/

Resultado correcto

Los símbolos !! confirman que Git está ignorando correctamente los archivos .log y la carpeta temporal.

Paso 9

Guardamos los cambios de .gitignore.

Las nuevas reglas forman parte de nuestro proyecto, por eso debemos guardarlas en un commit: 

git add .gitignore
git commit -m "Agregamos reglas para logs y temporales"

Guardamos .gitignore, pero Git no agregará errores.log, prueba.log ni la carpeta temporal.

¿Qué hicimos?

Creamos archivos .log y una carpeta temporal

↓

*.log

Ignora todos los archivos terminados en .log

↓

temporal/

Ignora toda la carpeta temporal

↓

Git deja de mostrar esos archivos

¿Qué aprendimos?

El símbolo * representa cualquier nombre. Por eso *.log ignora todos los archivos que terminan en .log.

La barra final / indica una carpeta. Por eso temporal/ ignora esa carpeta y todo lo que contiene. 

borrador.txt # Un archivo
*.log # Varios archivos
temporal/ # Una carpeta
22

Guardar cambios con un solo comando

Normalmente usamos dos comandos para guardar los cambios:

git add para llevar los cambios al Área de preparación.

git commit para guardarlos en el repositorio local.

Ahora aprenderemos el comando git commit -am, que permite guardar con un solo paso los cambios de archivos que Git ya conoce.

¿Desde dónde comenzamos?

El archivo index.html ya fue guardado en commits anteriores. Por eso Git ya lo está siguiendo. 

$ git log --oneline

94886bd (HEAD -> master) Agregamos reglas para logs y temporales
5dcd7f5 Agregamos archivo gitignore
42878e5 Agregamos página nosotros
02d6fae Agregamos páginas de servicios y galería

Idea principal

Como index.html ya tiene commits anteriores, podremos modificarlo y guardarlo utilizando git commit -am.

Paso 1

Abrimos index.html.

Abrimos el archivo principal de nuestro sitio web con Nano: 

nano index.html

¿Qué hace Nano?

Nano es un editor de texto que funciona dentro de Git Bash. Nos permite abrir, escribir, guardar y cerrar un archivo.

Paso 2

Escribimos el esqueleto de index.html.

Como index.html está vacío, dentro de Nano pegamos el siguiente esqueleto básico de una página HTML: 

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Mi primera página</title>
</head>
<body>

    <h1>Bienvenidos a nuestro sitio web</h1>

    <p>Estamos aprendiendo Git.</p>

</body>
</html>

¿Qué contiene este esqueleto?

<head> contiene información sobre la página, como su título.

<body> contiene lo que verá la persona al abrir la página.

<h1> crea el título principal y <p> crea un párrafo.

Paso 3

Guardamos y salimos de Nano.

1. Presionamos Ctrl + O

Para guardar el archivo.

2. Presionamos Enter

Para confirmar el nombre index.html.

3. Presionamos Ctrl + X

Para salir de Nano.

Paso 4

Revisamos el cambio realizado.

Git detectará que modificamos index.html: 

git status --short
 M index.html

¿Qué significa M?

La letra M significa Modified, es decir, modificado.

Git ya conocía index.html, pero detectó que modificamos su contenido después de su último commit.

Paso 5

Guardamos el cambio con un solo comando.

Como index.html ya es un archivo conocido por Git, utilizamos: 

git commit -am "Actualizamos texto de inicio"

¿Qué significa -a?

La opción -a agrega automáticamente los cambios de archivos que Git ya conoce.

En este caso agrega automáticamente la modificación de index.html antes de crear el commit.

¿Qué significa -m?

La opción -m permite escribir el mensaje del commit dentro del mismo comando.

Paso 6

Interpretamos el resultado del commit. 

[master 3980273] Actualizamos texto de inicio
1 file changed, 3 insertions(+)

Git creó un nuevo commit con el mensaje Actualizamos texto de inicio.

También indica que modificamos un archivo y agregamos tres líneas de contenido.

¿Qué significa el aviso LF y CRLF? 

warning: in the working copy of 'index.html',
LF will be replaced by CRLF the next time Git touches it

LF y CRLF son dos formas distintas de representar un salto de línea.

Este aviso aparece con frecuencia en Windows. No impidió que Git guardara el commit, por eso continuamos normalmente.

Paso 7

Confirmamos que no hay cambios pendientes. 

git status
On branch master
nothing to commit, working tree clean

working tree clean significa que todos los cambios fueron guardados y no existe nada pendiente.

Paso 8

Revisamos el nuevo commit. 

git log --oneline
3980273 (HEAD -> master) Actualizamos texto de inicio
94886bd Agregamos reglas para logs y temporales
5dcd7f5 Agregamos archivo gitignore

El commit nuevo aparece arriba porque es el cambio más reciente.

Paso 9

Creamos un archivo nuevo.

Ahora crearemos una página llamada equipo.html. Este archivo será nuevo, por lo tanto Git todavía no lo conocerá. 

touch equipo.html
git status --short
?? equipo.html

Los signos ?? indican que equipo.html es un archivo nuevo y Git todavía no lo está siguiendo.

Paso 10

Guardamos correctamente equipo.html.

Como equipo.html es un archivo nuevo, no utilizamos git commit -am. Primero debemos agregarlo al Área de preparación: 

git add equipo.html
git commit -m "Agregamos página equipo"

Error que debemos evitar 

fatal: pathspec 'equipo.html' did not match any files

Este mensaje aparece cuando Git recibe equipo.html como un archivo que debería conocer, pero todavía no fue agregado con git add.

La solución es utilizar primero: git add equipo.html.

¿Qué aprendimos?

Archivo que Git ya conoce

index.html

↓

git commit -am "Mensaje"

↓

Se guarda con un solo comando

Archivo nuevo

equipo.html

↓

git add equipo.html

↓

git commit -m "Mensaje"

Resumen

Para guardar cambios de archivos que Git ya conoce utilizamos: 

git commit -am "Mensaje del commit"

La opción -a agrega automáticamente los cambios de archivos rastreados.

La opción -m permite escribir el mensaje del commit.

Para un archivo nuevo siempre utilizamos primero git add.

Solucionar un archivo nuevo que no se guardó

En la lección anterior guardamos correctamente equipo.html. En esta lección crearemos un archivo distinto: clientes.html. En este caso no hacemos caso a la advertencia e intentamos guardarlo con git commit -am. Ahora veremos qué ocurrió y cómo solucionarlo correctamente.

Preparamos el caso

Creamos una página nueva llamada clientes.html. Git todavía no conocerá este archivo.

touch clientes.html

La situación: intentamos guardar sin agregar

Usamos este comando para intentar guardar un archivo que Git todavía no conocía: 

git commit -am "Agregamos página clientes"
On branch master
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        clientes.html

nothing added to commit but untracked files present
(use "git add" to track)

No se creó ningún commit. -a solo incluye archivos que Git ya estaba siguiendo; no agrega archivos nuevos.

¿Qué nos dijo Git en la pantalla?

1. On branch master

Solo informa que estamos trabajando en la rama master. No es un error.

2. Untracked files: clientes.html

Git encontró clientes.html, pero todavía no lo conoce ni lo está siguiendo.

3. nothing added to commit

Significa: no se agregó nada para guardar. Por eso el comando no creó el commit que intentábamos realizar.

La misma terminal nos da la pista

El mensaje indica use "git add <file>...". Git nos está diciendo que primero debemos ejecutar git add clientes.html.

Paso 1

Revisamos el estado del archivo.

Primero confirmamos qué cambios están pendientes:

git status --short
?? clientes.html

¿Qué significa ??

Significa que clientes.html existe en la carpeta, pero Git aún no lo está siguiendo.

Paso 2

Agregamos el archivo al Área de preparación.

Esta vez sí usamos git add:

git add clientes.html

Con este comando Git comienza a seguir el archivo y lo deja listo para guardar.

Paso 3

Confirmamos que está preparado.

git status --short
A  clientes.html

¿Qué significa A?

A significa Added: el archivo nuevo ya está en el Área de preparación.

Paso 4

Guardamos el archivo correctamente.

Ahora usamos git commit -m, sin la opción -a:

git commit -m "Agregamos página clientes"
[master 7ab39e1] Agregamos página clientes
1 file changed, 0 insertions(+), 0 deletions(-)
create mode 100644 clientes.html

Git creó el commit y ahora clientes.html ya forma parte del historial.

Paso 5

Comprobamos que ya no hay nada pendiente. 

git status
On branch master
nothing to commit, working tree clean

¿Qué aprendimos?

Archivo nuevo: clientes.html

↓

git add clientes.html

↓

git commit -m "Mensaje"

↓

Archivo guardado en Git
