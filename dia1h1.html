1

¿Qué es Git?

Git es una herramienta de control de versiones.
Te permite guardar el historial de tu proyecto.

Ejemplo:

¿Por qué usamos Git?

Nuestro jefe puede pedirnos que cambiemos el color de una parte de una página web y, después de ver el resultado, decirnos que el color anterior era mejor.

Si utilizamos Git, podemos volver a la versión anterior sin tener que recordar ni rehacer manualmente todos los cambios.

2

Git vs GitHub

Git: sirve para guardar los cambios que hacemos en nuestro proyecto en local y poder volver a una versión anterior si lo necesitamos.

GitHub: sirve para guardar nuestro proyecto en Internet. Así podemos tener una copia en línea, compartirla y trabajar con otras personas.

Git guarda los cambios en nuestra computadora y GitHub nos permite subir ese trabajo a Internet.

7

¿Qué es el archivo .gitignore?

El archivo .gitignore sirve para indicarle a Git qué archivos o carpetas no queremos guardar.

Para crear el archivo sigue estos pasos:

Paso 1

En Git Bash dentro de la carpeta de nuestro proyecto y escribimos:

touch .gitignore

Crea un archivo llamado .gitignore dentro de nuestro proyecto.
Paso 2

Abrimos el archivo .gitignore

Dentro del archivo podemos indicar que archivo o carpeta queremos ignorar de la siguiente manera:
  • Archivo: Colocamos el nombre completo del archivo. contraseña.txt
  • Carpeta: Colocamos el nombre de la carpeta seguido de /. privado/
  • Varios archivos: Colocamos cada archivo en una línea diferente.
    contraseña.txt
    datos.txt
    prueba.txt
  • Varios tipos de archivos: Utilizamos * para ignorar todos los archivos que tengan la misma extensión. *.log
  • Archivos y carpetas: Podemos combinar diferentes elementos.
    contraseña.txt
    privado/
    node_modules/
    *.log
Paso 3

Podemos generar un .gitignore automáticamente

Podemos utilizar una página que nos ayuda a generar el contenido del archivo .gitignore según la tecnología que utilizamos. 

https://www.toptal.com/developers/gitignore

Escribimos la tecnología que estamos utilizando, y presionamos Create.

La página generará el contenido que podemos copiar y pegar dentro de nuestro archivo .gitignore .

11

Agregar todos los archivos con Git

En la lección anterior utilizamos git add index.html para preparar un solo archivo.

Pero si nuestro proyecto tiene varios archivos, podemos utilizar: git add . para preparar todos los cambios del directorio actual.

Paso 1

Creamos nuevos archivos en nuestro proyecto.

Continuamos trabajando dentro de la carpeta proyecto1 .

En Git Bash escribimos: 

touch estilos.css

Presionamos Enter .

Después escribimos: 

touch script.js

Y nuevamente presionamos Enter .

Paso 2

Revisamos el estado del proyecto.

Escribimos: 

git status

Después presionamos Enter .

Untracked files: 

estilos.css
script.js

Significa:
Tenemos archivos nuevos sin seguimiento.

Git detectó los dos archivos, pero todavía no están preparados para incluirlos en un commit.

¿Qué debemos hacer ahora?

Podríamos agregar cada archivo por separado, pero aprenderemos una forma más rápida para preparar todos los cambios.

Paso 3

Preparamos todos los cambios.

En lugar de escribir un comando para cada archivo, escribimos: 

git add .

Después presionamos Enter .

git add

Significa:
Preparar cambios para incluirlos en el próximo commit.

.

El punto . representa el directorio actual.

Por eso, git add . prepara los cambios encontrados dentro del directorio actual y sus subdirectorios.

¿Cuál es la diferencia?

git add index.html
Prepara específicamente index.html.

git add .
Prepara todos los cambios del directorio actual.

Importante: antes de utilizar git add . debemos revisar qué archivos estamos preparando, porque puede incluir varios cambios al mismo tiempo.

Paso 4

Comprobamos los archivos preparados.

Escribimos nuevamente: 

git status

Después presionamos Enter .

Changes to be committed:

Significa:
Cambios preparados para el próximo commit. 

new file:   estilos.css
new file:   script.js

Los dos archivos aparecen en verde, por lo tanto ambos están preparados.

¿Qué debemos hacer ahora?

Como los dos archivos están preparados, realizaremos un nuevo commit.

Paso 5

Registramos los nuevos archivos.

Escribimos: 

git commit -m "Agregamos estilos y script"

Después presionamos Enter .

git commit

Significa:
Registrar los cambios preparados en el historial de Git.

Ahora este será nuestro segundo commit, porque ya realizamos uno en la lección anterior.

12

¿Dónde pasan nuestros archivos en Git?

Ya aprendimos a crear archivos, prepararlos con git add y registrarlos con git commit.

Ahora vamos a entender qué ocurre con nuestros archivos durante ese proceso.

1

Directorio de trabajo

Working Directory

Es simplemente la carpeta donde estamos trabajando con nuestro proyecto.

En nuestro ejercicio es: proyecto1

Allí tenemos nuestros archivos: 

index.html
estilos.css
script.js

En palabras sencillas: aquí es donde creamos y modificamos nuestros archivos.

Cuando queremos preparar nuestros cambios usamos:

git add .

↓

2

Área de preparación

Staging Area

Es una zona intermedia de Git.

Aquí quedan preparados los cambios que queremos registrar en nuestro próximo commit.

Nosotros ya vimos esta etapa cuando git status mostró: 

Changes to be committed:

new file:   estilos.css
new file:   script.js

En palabras sencillas: los archivos están preparados, pero todavía no hemos creado el commit.

Para registrar esos cambios usamos:

git commit -m "mensaje"

↓

3

Repositorio local

Local Repository

Aquí Git mantiene el historial de los commits de nuestro proyecto.

En nuestro ejercicio vimos: 

[master b720efd] Agregamos estilos y script
2 files changed

Ese mensaje confirmó que Git registró nuestro nuevo commit.

En palabras sencillas: aquí quedan registrados nuestros commits y su historial.

Ahora entendamos el recorrido completo

DIRECTORIO DE TRABAJO

Creamos y modificamos

↓

git add .

↓

ÁREA DE PREPARACIÓN

Preparamos los cambios

↓

git commit

↓

REPOSITORIO LOCAL

Registramos el commit

Piénsalo de esta manera

Imagina que estás preparando documentos para guardarlos.

Directorio de trabajo: es tu mesa de trabajo, donde creas y modificas los documentos.

Área de preparación: seleccionas cuáles cambios quieres incluir en el próximo registro.

Repositorio local: Git registra ese conjunto de cambios como un commit dentro del historial del proyecto.

13

Ver el historial de commits

Ya realizamos dos commits en nuestro proyecto.

Ahora aprenderemos a consultar el historial de commits para saber qué cambios hemos registrado anteriormente.

Paso 1

Consultamos el historial de commits.

Dentro de nuestra carpeta proyecto1 escribimos: 

git log

Después presionamos Enter .

git log

Significa:
Mostrar el historial de commits de nuestro repositorio.

Paso 2

Observamos nuestros commits.

En nuestro ejercicio aparece algo como: 

commit b720efde40ad0b84d820507496bde62b97473cf1 (HEAD -> master)
Author: Darío Sossa <dario@gmail.com>
Date:   Sat Sep 19 09:49:46 2026 -0400

    Agregamos estilos y script

commit a4b383ab2ed50d3bf281eeb4124732c40135de15
Author: Darío Sossa <dario@gmail.com>
Date:   Sat Sep 19 09:29:42 2026 -0400

    Primer commit

Importante: cada estudiante verá sus propios identificadores, nombre, correo, fecha y hora.

Paso 3

Entendemos lo que muestra git log.

commit b720efde40ad0b84d820507496bde62b97473cf1

commit nos indica que estamos viendo un registro guardado en el historial.

La combinación de letras y números es el identificador del commit.

Cada commit tiene su propio identificador.

HEAD -> master

HEAD señala el commit en el que estamos ubicados actualmente.

master es la rama en la que estamos trabajando.

En nuestro caso, HEAD está apuntando al último commit de la rama master.

Author: Darío Sossa <dario@gmail.com>

Author significa autor.

Nos muestra el nombre y correo asociados al autor del commit.

Date: Sat Sep 19 09:49:46 2026 -0400

Date significa fecha.

Indica la fecha y hora asociadas a ese commit.

Agregamos estilos y script

Este es el mensaje que escribimos cuando realizamos el commit.

Nos ayuda a identificar qué registramos en ese momento.

Paso 4

Identificamos el orden de los commits.

Git muestra primero el commit más reciente y después los anteriores. 

Agregamos estilos y script
        ↓
Primer commit

Por eso podemos leer el historial desde el cambio más reciente hacia los anteriores.

Paso 5

Vemos el historial de forma resumida.

Ahora escribimos: 

git log --oneline

Después presionamos Enter .

En nuestro ejercicio apareció: 

b720efd (HEAD -> master) Agregamos estilos y script
a4b383a Primer commit

--oneline

oneline significa en una línea.

Git muestra cada commit de manera resumida, utilizando el identificador abreviado y el mensaje del commit.

Paso 6

Comparamos las dos formas.

git log

Muestra información detallada: identificador, autor, fecha y mensaje.

git log --oneline

Muestra el historial de forma resumida, con un commit por línea.

¿Qué aprendimos?

Los commits que realizamos no desaparecen después de crearlos. Forman parte del historial de nuestro repositorio.

Podemos consultar ese historial con git log o verlo de manera resumida con git log --oneline.

Es el identificador abreviado del commit.

En lugar de mostrar el identificador completo, Git nos muestra una versión más corta.

(HEAD -> master)

Nos indica que actualmente estamos trabajando en la rama master.

HEAD señala nuestra posición actual dentro del historial.

En este momento, HEAD apunta al commit más reciente de master.

Paso 4

Entendemos por qué aparece una sola línea.

Nuestro historial actualmente puede imaginarse así:

● b720efd (HEAD → master)
│
● a4b383a Primer commit

Los dos commits aparecen uno debajo del otro porque hasta ahora hemos trabajado solamente en una rama: master.

Más adelante, cuando creemos otras ramas, este gráfico nos permitirá observar cómo el historial puede dividirse en diferentes líneas de trabajo.

Paso 5

Entendemos cada parte del comando.

git log

Muestra el historial de commits.

--oneline

Muestra cada commit resumido en una sola línea.

--graph

Dibuja una representación gráfica del historial utilizando líneas y símbolos.

--decorate

Muestra referencias como HEAD y el nombre de la rama master.

--all

Permite que el gráfico considere todas las referencias disponibles, incluidas las ramas.

Por ahora solamente tenemos master, pero este parámetro será más útil cuando creemos otras ramas.

¿Qué aprendimos?

Podemos utilizar
git log --oneline --graph --decorate --all
para observar de forma visual el historial de nuestro proyecto.

Por ahora vemos una sola línea porque únicamente estamos trabajando en master.

Cuando creemos una nueva rama podremos volver a ejecutar este comando y observar cómo cambia el gráfico.
